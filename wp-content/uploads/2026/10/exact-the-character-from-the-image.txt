This is actually one of the most interesting parts of AI applications like ToonyStory. They almost certainly do not store the AI model itself or retrain it for each user. Instead, they store a combination of the original images, metadata, and AI-generated character information so they can recreate the character consistently.

Here's how a typical pipeline works.

Step 1: User uploads photos

Suppose a user uploads three photos of their child.

The AI extracts descriptive information such as:

Why save the character instead of the generated images?

Imagine a user creates ten different books.

Without a saved character, the user would have to:

upload photos again
wait for analysis again
risk the AI interpreting the photos differently each time

By storing a reusable character profile, the system can generate new stories with the same character much more efficiently and consistently.

In short

The magic is not a single AI call. It is a pipeline:

Store the user's character profile.
Retrieve character information.
Ask an LLM to create a structured story.
Convert each page into an image description.
Combine character reference + scene prompt.
Generate illustrations.
Store pages/images.
Assemble everything into a book.

The hardest engineering problem is not story generation — LLMs are already very good at that. The hardest problem is maintaining the same character identity across 20–50 generated illustrations, which requires reference images, embeddings, prompt engineering, or specialized fine-tuning techniques.

Why not directly store the image in PostgreSQL?

Technically you can:

CREATE TABLE images (
 id INT,
 image BYTEA
);

But AI applications usually avoid it because:

❌ Database becomes huge
❌ Backups become expensive
❌ Slower queries
❌ Harder CDN delivery

Instead:

Database
   |
   | stores metadata
   |
   ▼

Cloud Storage
   |
   | stores actual files
   |
   ▼

Images/Videos/PDFs

So the answer is:

The image is stored in the database only after the AI image generation finishes, the image is uploaded/copied into permanent storage, and then the database saves the URL and metadata pointing to that image. The database stores the "address and information about the image", not usually the image file itself.
